# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

HabiTracker: an Expo (SDK 58) + React Native + TypeScript app using Expo Router for file-based navigation. Implements a local-first habit tracker: daily and quantity habits, streaks, history, multi-habit challenges, per-habit reminders (local notifications), and haptic/sound/confetti rewards. Every read and write hits an on-device cache; a background sync copies it to a Supabase (Postgres) account behind email + password sign-in.

Design specs are dated files in `docs/superpowers/specs/`, with the matching implementation plan in `docs/superpowers/plans/`. The habit-tracker redesign spec covers the app itself; the Supabase sync/auth spec covers accounts and sync, including its non-goals (no social login, password reset UI, account deletion UI or Realtime) — check those before "fixing" something that was left out on purpose.

The sync core has automated checks, and the full flow has been run on web against the live Supabase project (sign-up/sign-in, multi-device sync, offline queue, merge, sign-out, reset, cross-account isolation). Everything native (SQLite cache, SecureStore session, sync on a phone) has not been run yet — treat it as untested rather than known-good.

## Commands

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm add — resolves SDK-compatible versions
npm start                   # or: npx expo start — dev server (scan QR with Expo Go, or press a/i/w)
npm run android / ios / web # start targeting a specific platform
npx tsc --noEmit            # typecheck
npm run lint                # expo lint (ESLint)
npx expo-doctor             # diagnose dependency/config issues
npx expo install --fix      # fix incompatible package versions
node scripts/check-sync.mjs # sync/merge checks (node:test, no dependencies)
node scripts/check-coach.mjs # checks for the stats the AI coach is given
npx supabase db push        # apply supabase/migrations/ to the linked project (asks for the DB password)
npx supabase functions deploy coach-nudge reflection-report  # deploy the edge functions
cd supabase/functions && npx deno@2 check coach-nudge/index.ts reflection-report/index.ts  # typecheck them
```

Run `npx tsc --noEmit` and `npm run lint` before declaring any task done, plus `node scripts/check-sync.mjs` after touching anything in `src/lib/sync/` or `src/lib/habit-logic.ts`. There is no other test runner. Those checks import the TypeScript sources directly through Node's type stripping, so the modules they load (`replica`, `rows`, `habit-store`, `sync-engine`, `remote-store-fake`, `habit-logic`) must stay free of React/Expo imports and of non-erasable TS syntax (enums, parameter properties, namespaces).

Supabase needs `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in a git-ignored `.env.local` (template: `.env.example`); they are inlined when the bundle is built, so restart the dev server after changing them. Without them the app runs local-only with no sign-in gate — a supported mode, not an error. Only the publishable key belongs in the app; the `service_role` key and the database password never go in the repo. The Supabase CLI refuses to prompt inside an agent shell: `supabase login` / `link` / `db push` have to be run by the user in their own terminal (add `--agent no` if it still answers in JSON).

For layout changes, `npm run web` in a browser at phone and desktop sizes is the quickest check, but it only covers the web variants — the tab bar and top spacing are implemented separately for native (see Architecture), so native needs a device or emulator.

`npm run lint` is clean; keep it that way. (The web color-scheme and tab-bar hooks use `useSyncExternalStore` for their "hydrated yet?" flag instead of setting state in an effect, which the `react-hooks/set-state-in-effect` rule rejects.)

## Expo changes fast — verify before coding against its APIs

Expo ships breaking changes every SDK release; APIs remembered from training data are often renamed, moved, or removed. Before writing code against any Expo/EAS/React Native API:
1. Check the `expo` major version in `package.json` (currently SDK 58).
2. Check the matching versioned docs: `https://docs.expo.dev/versions/v58.0.0/`.
3. For anything else, check `https://docs.expo.dev/llms.txt` (index of docs with corrections to common LLM misconceptions) and follow its links — don't answer from memory.

Prefer Expo's own modules over third-party libraries. The `expo` Claude Code plugin is enabled in `.claude/settings.json`; check its skills before adding a dependency or working against an Expo API.

## Architecture

- **Entry point:** `package.json` `main` is `expo-router/entry` → resolves to `src/app/_layout.tsx` (root layout: wraps the app in `ThemeProvider`, `AuthProvider` and `HabitsProvider` — in that order, since habits depend on who is signed in — then renders `AnimatedSplashOverlay` and the gates described below).
- **Routing:** file-based via Expo Router, rooted at `src/app/` (not the default `app/` — see `tsconfig.json` paths). Every file under `src/app/` is a screen; `_layout.tsx` files define navigators. Keep non-route code (components, hooks, constants) out of `src/app/`.
- **Tabs (dual implementation):** `src/components/app-tabs.tsx` (native platforms, built on `expo-router/native-tabs`, whose `md` icons need `expo-symbols` installed on Android) and `app-tabs.web.tsx` (web, built on `expo-router/ui` `Tabs`/`TabList`/`TabTrigger`) are separate implementations of the same tab bar — Metro picks the `.web.tsx` variant automatically on web via the platform-extension convention. When changing tabs/navigation, both files need updating together. Tabs: Today (`index`), History, Manage, Challenge, Settings — one screen file each in `src/app/`.
- **Root gating:** `Root` in `src/app/_layout.tsx` picks at most one gate to show instead of the tabs: `AuthScreen` (signed out, and either onboarding is done or "I already have an account" was tapped), a "Loading your habits…" screen (signed in on a device with no data yet, until the first sync answers), or `OnboardingScreen` (until `onboardingComplete`). So a new user onboards first and creates an account after; a returning user signs in and skips onboarding. On web the gate is an overlay on top of an always-mounted navigator (so deep links/reloads keep their route); on native it replaces the tabs, since native tab bars can't be covered.
- **Theming:** `src/constants/theme.ts` defines `Colors` (light/dark palettes), `Spacing` scale, and `Fonts`. `src/hooks/use-theme.ts` and `use-color-scheme(.web).ts` resolve the active scheme. `src/components/themed-text.tsx` / `themed-view.tsx` are the base styled primitives — use these instead of raw RN `Text`/`View` so components stay color-scheme-aware.
- **Screen layout:** `src/components/screen.tsx` is the shared page shell (title, `ScrollView`, max content width, top/bottom spacing) used by every tab and by onboarding — except Today (`src/app/index.tsx`), which has its own layout: a vertically centered block with a `FlatList`, capped at the screen height so it can't overflow off the top. Top spacing is platform-specific in both: native adds the safe-area inset to `Spacing.three`; web uses a fixed `Spacing.six + Spacing.three` to clear the web tab bar, which is absolutely positioned over the top of the page. Changing the web tab bar's height means updating that padding in both files. Bottom spacing uses `BottomTabInset` from `theme.ts`.
- **Web CSP:** `src/app/+html.tsx` (the SDK 58 root HTML: `useServerDocumentContext()`, with `headNodes`/`bodyNodes`) puts the Content-Security-Policy from `src/lib/csp.ts` on production web pages: scripts only from the site (plus Expo's one inline hydration line, allowed by `EXPO_HYDRATE_SCRIPT_HASH`), requests only to the site, the Supabase origin and, when CAPTCHA is on, Turnstile. A new external origin (API, CDN, font) has to be added there. If an Expo upgrade changes the inline hydration script, the browser console reports a CSP violation; recompute the hash from the exported `index.html`. A meta tag can't set `frame-ancestors`, so the root layout itself refuses to render inside another site's frame (`useFramed`, `src/hooks/use-framed(.web).ts`) against clickjacking. `app-tabs.web.tsx` uses the narrow layout until hydration finishes (the static HTML is rendered in Node, which has no window width), so the first render matches the HTML.
- **Path aliases:** `@/*` → `src/*`, `@/assets/*` → `assets/*` (defined in `tsconfig.json`).
- **Habit state:** `src/hooks/use-habits.ts` exports `HabitsProvider` and `useHabits()` — what screens use for habits, history, challenge, settings and the onboarding flag. Mutators update an in-memory store synchronously (the UI never waits on disk or network); persistence and sync follow in the background. The same file exports `useSync()` (sync status, pending count, `syncNow`, `signOut`, the one-off merge notice). `resetAll` erases the account first when signed in and rejects if it can't be reached, so nothing is half-erased.
- **Local cache:** `src/lib/sync/` holds the store (`habit-store.ts`), the replica — app state plus per-row sync bookkeeping (`replica.ts`) — and its persistence (`persister.ts` → `local-store.ts`, SQLite `habitracker.db` on native / `local-store.web.ts`, one AsyncStorage key on web). The old per-piece `habit-tracker/*` AsyncStorage keys (`KEYS` in `use-habits.ts`) are read once to migrate existing installs and then removed; neither they nor the `habit-tracker/` prefix may be renamed, or those installs lose their data. The dev day offset is still stored there and never syncs.
- **Sync:** `sync-engine.ts` pulls then pushes through the `RemoteStore` interface (`remote-store.ts`; `remote-store-supabase.ts` in the app, `remote-store-fake.ts` in the checks), on launch, foreground, regained connectivity and (debounced) after local writes, retrying with backoff. Conflicts resolve per row by latest `updated_at`, except history, where the higher `count` wins so a check-off is never lost — the same rule is enforced in Postgres by a trigger. Schema, Row Level Security (each user sees only their own rows) and the `reset_my_data()` function live in `supabase/migrations/`; change the database only by adding a migration there, and keep `rows.ts` (row ⇄ app-type mapping) in step with it. New tables in `public` get RLS switched on automatically (the `ensure_rls` event trigger, `20261122000300_rls_auto_enable.sql`), but their migration still has to add policies and grants. The database limits what clients write (names ≤ 200 characters, ids ≤ 64, no negative counts, small JSON; `20261122000100_size_limits.sql`); the app keeps names to `NAME_MAX` (100) with `cleanName()` in `habit-logic.ts`, on input, on load (`migrateHabit`) and on pull (`toHabit`/`toChallenge` in `replica.ts`), so it never writes a row the server rejects.
- **Auth:** `src/hooks/use-auth.ts` (`AuthProvider`, `useAuth()`) wraps Supabase email + password auth; `status` is `loading | signedIn | signedOut | disabled` (`disabled` = no Supabase env vars). `src/lib/supabase.ts` creates the client lazily — static web export runs this code in Node, so nothing there may touch `window` at import time. Sessions are stored via `session-storage.ts` (`expo-secure-store`) / `session-storage.web.ts` (`localStorage`). Signing out clears the local cache (Settings syncs first and warns if changes would be lost); signing in on a device that already has local habits merges them into the account. "Forgot password?" (`password-reset.tsx`) uses a code typed into the app, not a link, so it needs no deep links or redirect URLs: `resetPasswordForEmail` → `verifyOtp({ type: 'recovery' })` → `updateUser({ password })`. The verified code already creates a session, so `use-auth.ts` parks auth changes (`resetHold`) until the new password is saved — the app must not open before then. The Supabase "Reset password" email template has to contain `{{ .Token }}` (the default one only has a link). Sign-in, sign-up and the reset email send a Cloudflare Turnstile token when `EXPO_PUBLIC_TURNSTILE_SITE_KEY` is set (`src/lib/captcha.ts`; widget in `captcha.tsx`, a WebView page, / `captcha.web.tsx`); a token is accepted once, so the screens ask for a new one after every attempt. The project's auth settings (email confirmation on, 8-digit codes valid 15 minutes, secure password change, CAPTCHA) are in `supabase/config.toml` for the local stack only; the hosted project needs them set in the dashboard (README → Security settings).
- **AI coaching:** app → Supabase Edge Function → Google Gemini API (REST `generateContent`, default `gemini-3.8-flash`, override with the `GEMINI_MODEL` secret; `gemini-2.5-*` is deprecated). When a model is overloaded (503), out of quota (429) or slower than 40 s, the function moves on to `gemini-3.6-flash` (`GEMINI_FALLBACK_MODEL`) and then `gemini-3.5-flash-lite`, staying inside the edge function's time limit (exceeding it gives a 546). This follows the flow diagram the feature was specced from. `supabase/functions/coach-nudge` writes the daily nudge on Today (`coach-card.tsx`), and `reflection-report` writes the weekly/monthly reflection in History (`reflection-card.tsx`); both go through `src/lib/coach.ts` + `src/hooks/use-coach.ts`. A function verifies the caller's session, reads their habits/history/challenge with their own token (so RLS applies), computes every number in `_shared/stats.ts` (pure, checked by `scripts/check-coach.mjs`), and has the model write only the words, as JSON constrained by `responseJsonSchema` (built from the zod schemas, nullable objects rewritten from `anyOf` to type arrays) and re-validated with zod. Results are cached per period in `coach_insights`; each model call is logged in `coach_usage` (service-role only). A call claims its slot before the model is asked, through `claim_coach_call()` (one locked statement: 10 calls per user per 24 hours, and `COACH_GLOBAL_DAILY_LIMIT`, default 2000, for the whole project), so simultaneous requests can't get past either cap. `loadInput` reads at most 50 habits and only their history, `stats.ts` cuts names to 80 characters, and answers are capped at 4096 output tokens; together they bound what one account can make a call cost. The functions are Deno: they're excluded from the app's `tsc`, import packages as `npm:` specifiers, and need the `GEMINI_API_KEY` Supabase secret, which is set by the user, never committed. The coach is signed-in only and can be switched off with the synced `aiCoach` setting.
- **Pure logic:** `src/lib/habit-logic.ts` holds the types (`Habit`, `HistoryEntry`, `Challenge`, `Settings`), date keys, day rollover, streak/count math, and storage migration (`migrateHabit`). Put rules there, not in components. "Today" comes from `getToday()`, which honors a dev-only day offset (Settings screen) for testing rollovers and challenges without waiting.
- **Rewards:** `src/hooks/use-habit-rewards.ts` wraps `setCount` and is the only module touching `expo-haptics`/`expo-audio`; it emits milestone/all-done events that drive `confetti-burst.tsx` and `streak-flame.tsx`. Its players come from `createAudioPlayer` in an effect (`useSoundEffect`), not `useAudioPlayer`: SDK 58's web `useAudioPlayer` builds an `<audio>` element during render, which breaks the static web export (pages render in Node). Sounds in `assets/sounds/` are synthesized by `node scripts/generate-sounds.js`.
- **Notifications:** `src/lib/notifications.ts` (native) and `notifications.web.ts` (no-op stub, same `.web` convention as the tabs) schedule per-habit reminders plus the afternoon-nudge and streak-at-risk alerts. `use-notification-sync.ts` (mounted in the root layout) reschedules when settings or habit reminders change and when the app backgrounds. Notifications need a development build, not Expo Go.
- **Continuous Native Generation:** no `ios/`/`android/` directories exist in this repo — they're generated on demand. Never hand-edit generated native projects; configure native behavior through `app.json` and config plugins.
- **Development builds:** Expo Go only bundles its own pre-included native modules. After adding any library with native code, a development build is required (`npx expo run:ios`/`run:android` locally, or `eas build --profile development`).
- **EAS:** cloud builds/signing/submission (`eas build`, `eas submit`) and OTA updates (`eas update`) run via `npx eas-cli@latest <command>`.

## Supabase schema and Edge Functions

Migrations in `supabase/migrations/` (applied in name order) are the only source of truth for the database. Every table is in `public` with Row Level Security on; `anon` has no table access.

| Table | Rows | Access |
| --- | --- | --- |
| `habits` | One per habit (`user_id`, `id`): name, type, target, today's count (`count_date`), streaks, reminder JSON, soft delete | own rows, CRUD |
| `history` | One per habit per day (`user_id`, `habit_id`, `date`): count, completed; a trigger keeps the higher count | own rows, CRUD |
| `challenges` | One per user: name, `habit_ids`, duration, start, progress, status | own row, CRUD |
| `user_state` | One per user: synced settings JSON, onboarding flag, last rollover date, `data_epoch` | own row, CRUD |
| `coach_insights` | AI output per user, `kind` (`nudge`/`weekly`/`monthly`) and period; `pushed_at` | read/delete own; written by functions |
| `coach_usage` | One per model call (model, tokens) | service role only |
| `push_tokens` | Expo push tokens (≤ 10 per user) | read/delete own; written via `register_push_token()` |

The coach's "profile" data (first name, time zone) is Supabase Auth `user_metadata`, not a table. Database functions: `touch_updated_at` / `history_keep_highest` (triggers), `reset_my_data()` (invoker), `register_push_token()` (definer, Expo-format tokens only), `claim_coach_call()` (service role; per-user and project-wide caps under one advisory lock), `rls_auto_enable()` with the `ensure_rls` event trigger (never blocks a `CREATE TABLE`). Client writes are size-checked (`20261122000100_size_limits.sql`). The pg_cron job `coach-hourly` calls `coach-scheduler` with URL and secret from Vault (`coach_scheduler_url`, `coach_cron_secret`).

Edge Functions (Deno, `supabase/functions/`, `verify_jwt = false` because each checks its caller itself): `coach-nudge` and `reflection-report` (app-facing; `auth.getUser()` first, data read with the caller's token) and `coach-scheduler` (cron only; constant-time check of `COACH_CRON_SECRET`). Shared code in `_shared/`: `coach.ts` (Gemini calls via REST `generateContent` with `responseJsonSchema` and `maxOutputTokens`, model fallback chain, `claim_coach_call`, bounded `loadInput`), `stats.ts` (all numbers; names cut to 80 characters), `nudge.ts` / `report.ts` (prompts and zod schemas), `schedule.ts`, `push.ts` (Expo push; tokens never logged). Secrets: `GEMINI_API_KEY`, `COACH_CRON_SECRET`, optional `GEMINI_MODEL`, `GEMINI_FALLBACK_MODEL`, `COACH_GLOBAL_DAILY_LIMIT`, `EXPO_ACCESS_TOKEN` (template: `supabase/.env.example`). Imports are pinned (`npm:@supabase/supabase-js@2.119.2`, `npm:zod@4.6.7/v4`) and locked in `supabase/functions/deno.lock`. Function logs must not contain user content or push tokens.
